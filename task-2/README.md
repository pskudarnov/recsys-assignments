# RL для рекомендаций: опыт на Yambda

Взял последовательности прослушиваний из [Yambda-50M](https://huggingface.co/datasets/yandex/yambda) и обучил модель предсказывать следующий трек. Затем дообучил её с подкреплением: награду задавала отдельная модель, которая прогнозирует долю прослушивания и возвращение пользователя. Проверил четыре варианта: в одном политика обучается по награде за ближайший шаг, в трёх – по наградам за пять шагов.

Лучший вариант по прогнозу доли прослушивания поднял её с 0,6537 до 0,6568 среди десяти рекомендаций. Одновременно Recall@10 по следующим прослушиваниям снизился с 0,0545 до 0,0529. Вариант со штрафами за повторы и популярность стал реже рекомендовать знакомые треки, но тоже потерял в Recall. Не нашёл настройку, которая заметно повышает прогноз награды и сохраняет точность.

Код, веса и подробные результаты лежат в этой папке. [Отдельный опыт на MovieLens 100K](MOVIELENS_REPORT.md) показывает, как тот же подход ведёт себя с рейтингами фильмов вместо прослушиваний.

## Данные и протокол

Взял файл `flat/50m/listens.parquet` из [Yambda-50M](https://huggingface.co/datasets/yandex/yambda). Чтобы опыт можно было повторить на обычном компьютере, оставил пользователей с `uid % 1000 == 0`: 916 человек и все их 4 551 217 прослушиваний. Это фиксированная часть набора, поэтому по ней нельзя судить о разбросе результатов между разными выборками пользователей. Скрипт скачивает ревизию `dd6f3a19eef5866e346c3270e098baa641a44948` и проверяет SHA-256 `eed9cbd094af1e189507d2f8132a0dc9653b90e65480125c7cdccd601e0592d1`.

Из каждой записи беру пользователя, трек, время, долю прослушивания, длительность трека и признак `is_organic`. Время округлено до пяти секунд, поэтому несколько треков одного человека могут иметь одинаковую метку.

Все события разделил по времени: обучение при `timestamp < 22081524`, валидация при `22081524 ≤ timestamp < 24091787`, тест после второй границы. Границы примерно соответствуют 80% и 90% событий и не разрезают события с одинаковым временем. В каталог попали 3000 самых частых треков **обучающего периода**. Треки вне каталога не становятся целями для рекомендателя, но учитываю их, когда определяю, вернулся ли пользователь.

Для каждого целевого трека в историю попадают только события с **более ранним** временем. Прослушивания с одинаковой меткой получают одну и ту же историю. Когда оцениваю событие в тестовом периоде, уже произошедшие события этого периода можно использовать как историю, но не как обучающие цели.

После этих ограничений доступны 1 196 099 обучающих, 132 781 валидационных и 118 665 тестовых примеров. Для базовой модели выбрал 150 000 обучающих событий, для валидации – 15 000. Из теста взял не более 20 событий на пользователя: всего 14 996 событий от 867 пользователей. Выбор фиксирован `seed=42`. Уже знакомые треки остаются среди кандидатов: в музыке повторное прослушивание бывает полезным. Внутри группы с одинаковым временем порядок неизвестен; при добавлении этой группы в последующую историю использую порядок по `item_id`.

Модель отклика предсказывает долю прослушивания и факт возвращения: запустил ли пользователь **хотя бы один** трек через 24 часа – 7 дней. Долю из `played_ratio_pct` ограничил диапазоном 0–100%: значения выше 100% в Yambda возможны, когда человек перематывает трек и слушает его части повторно ([описание поля](https://huggingface.co/datasets/yandex/yambda#what-does-it-mean-when-played_ratio_pct-is-greater-than-100)). Для сигнала возврата учитывал и треки вне каталога. События за последние семь дней каждого периода исключил из обучения и проверки возврата: иначе пришлось бы смотреть за границу периода. Возвращение могло произойти по любой причине; приписывать его исходному треку нельзя.

## Как обучил модели

**Базовая модель.** Небольшой каузальный Transformer: два блока, четыре головы внимания, ширина 64. На входе до 50 предыдущих треков. Обучил его с нуля, без готовых весов GPT-2; задача та же, что у языковой модели, только токенами служат треки. Использовал cross-entropy, AdamW, `lr=0.001`, batch 256, две эпохи. Ошибка на валидации снизилась с 7,749 до 7,381.

**Модель отклика.** Она получает историю, трек-кандидат, пользователя и длительность трека. Два выхода модели дают прогноз доли прослушивания и вероятности возвращения. Обучил её на 300 000 неорганических прослушиваний четыре эпохи: AdamW, `lr=0.001`, batch 256, потери `MSE + 0.2 × BCE`. На валидации выбрал эпоху и степень смешивания прогноза со средним по обучению (коэффициенты 0,76 и 0,43). Непрослушанные кандидаты в обучение не попадали.

**RL-дообучение.** Все варианты начинаются с одних и тех же весов. На каждом шаге беру 64 лучших кандидата базовой модели, выбираю один по текущей политике и добавляю его в историю. Модель отклика оценивает этот выбор. REINFORCE обновляет политику по сумме наград с дисконтом `γ=0.9`. Вычитаю средний дисконтированный возврат батча и добавляю штраф за отличие от исходной модели: `β·KL(π_base || π_RL)` по всему каталогу. Для каждого варианта использовал 3000 обучающих историй, batch 48, AdamW, `lr=0.0001`.

Сравнил четыре настройки: один шаг и доля прослушивания при `β=0.1`; пять шагов и доля при `β=0.03` и `β=0.3`; пять шагов и смешанная награда при `β=0.1`. Последняя равна `0.7 × прогноз доли + 0.3 × прогноз возврата − 0.1 × повтор − 0.05 × нормированная логарифмическая популярность`. Повтором считаю знакомый трек или трек, уже выбранный в этой синтетической последовательности. Популярность считаю только по обучающим данным.

Ограничение в 64 кандидата не даёт RL выбирать произвольный трек из каталога. Но даже для этих кандидатов награда остаётся прогнозом: реакции пользователей на сгенерированные рекомендации в данных не видны.

## Качество модели отклика

В тесте осталось 6632 неорганических прослушивания с известным исходом на следующие семь дней. RMSE прогноза доли прослушивания равен **0,3830** против **0,4260**, если всегда выдавать среднее по обучению. Для возвращения AUC равен **0,6797**, ошибка Brier – **0,1988** против **0,2186** у постоянного прогноза. У RMSE и Brier меньшее значение лучше.

На валидации после калибровки RMSE был 0,3837 против 0,4334, Brier – 0,1265 против 0,1329. Доля вернувшихся упала с 0,8423 на валидации до 0,7158 в тесте; ошибка Brier на тесте заметно выше. Все названные ошибки измерены на треках, которые действительно слушали; качество прогнозов для остальных кандидатов неизвестно.

## Сравнение политик на одном тесте

Все варианты проверены на одних и тех же 14 996 событиях. Модель выбирает десять треков без запрета повторов. Recall@10 показывает, встретился ли следующий прослушанный трек в этой десятке; NDCG@10 учитывает его место. Доля прослушивания и возврат в таблице – **прогнозы модели отклика** для рекомендованной десятки. Реакции на эти рекомендации в логах нет.

| Политика | Recall@10 | NDCG@10 | Предсказанная доля | Предсказанный возврат | Повторы Top-10 | Покрытие каталога | Доля 10 самых частых |
|---|---:|---:|---:|---:|---:|---:|---:|
| База | 0,0545 | 0,0303 | 0,6537 | 0,8160 | 51,0% | 49,7% | 15,3% |
| Один шаг, доля, β=0,1 | 0,0540 | 0,0303 | 0,6564 | 0,8159 | 52,1% | 47,9% | 17,6% |
| Пять шагов, доля, β=0,03 | 0,0529 | 0,0302 | **0,6568** | 0,8157 | 51,9% | 48,3% | 17,5% |
| Пять шагов, доля, β=0,3 | 0,0532 | 0,0300 | 0,6563 | 0,8161 | 50,6% | 50,0% | **14,1%** |
| Пять шагов, смешанная | 0,0527 | 0,0299 | 0,6555 | 0,8160 | **48,2%** | **53,0%** | 15,0% |

Среди прослушиваний на 80% и больше Recall@10 равен 0,0569 у базы и 0,0557 у варианта со смешанной наградой. Если оставить только неорганические прослушивания, результаты всех моделей ниже: 0,0292 у базы и 0,0266–0,0286 после RL. При равном весе каждого пользователя Recall@10 базы составляет 0,0544, у RL-вариантов – от 0,0527 до 0,0541. Для ориентира всегда рекомендовал десять самых популярных треков: получилось 0,0247 по Recall@10 и 0,0094 по NDCG@10. Полные числа есть в `yambda_results/audit.json`.

Чтобы не считать события одного человека независимыми, построил парные 95% интервалы разницы Recall@10 по **867 пользователям**. В бутстрэпе 3000 повторов; в таблице RL сравнивается с базой.

| RL-вариант | Разница пользовательского Recall@10 | 95% интервал |
|---|---:|---:|
| Один шаг | −0,00026 | [−0,00184; 0,00139] |
| Пять шагов, β=0,03 | −0,00160 | [−0,00301; −0,00018] |
| Пять шагов, β=0,3 | −0,00087 | [−0,00225; 0,00050] |
| Смешанная награда | −0,00169 | [−0,00328; −0,00020] |

При `β=0.03` и смешанной награде весь интервал ниже нуля. На этом тесте падение Recall@10 небольшое, но оно повторяется у разных пользователей. Для двух других вариантов интервал охватывает ноль. У NDCG@10 все интервалы охватывают ноль. Поправку на несколько сравнений не делал, поэтому не считаю эти интервалы окончательным статистическим подтверждением.

При `β=0.03` десять самых часто рекомендуемых треков заняли 17,5% всех мест против 15,3% у базы. Повторы выросли с 51,0% до 51,9%. При `β=0.3` концентрация упала до 14,1%, а Recall@10 остался близок к исходному. Смешанная награда уменьшила повторы до 48,2% и подняла покрытие каталога до 53,0%, но за счёт части Recall@10. Средняя длина рекомендованного трека во всех вариантах была от 188,0 до 192,4 секунды при 191,5 у базы. Опасения, что модель начнёт выбирать только короткие треки, в этом запуске не подтвердились.

## Генерация пяти шагов

Для 200 пользователей взял первую историю из теста. Модель предложила один трек, добавил его в историю и повторил выбор ещё четыре раза. Для сравнения отдельно добавлял действительно прослушанные позже треки. При одинаковой временной метке брал только один трек, потому что порядок внутри такой группы неизвестен. Этот опыт показывает, как меняются рекомендации после добавления **предполагаемых**, а не подтверждённых прослушиваний.

| Политика | Прогноз доли, шаг 1→5 | Прогноз возврата, шаг 1→5 | Повторы, шаг 1→5 | Совпадение Top-10 синтетического и реального контекста, шаг 1→5 |
|---|---|---|---|---|
| База | 0,6653 → 0,6635 | 0,8022 → 0,7990 | 61,5% → 86,0% | 100% → 27,1% |
| Один шаг | 0,6687 → 0,6669 | 0,7998 → 0,7985 | 62,5% → 90,0% | 100% → 29,0% |
| Пять шагов, β=0,03 | 0,6686 → 0,6662 | 0,7988 → 0,7982 | 62,5% → 89,0% | 100% → 29,0% |
| Пять шагов, β=0,3 | 0,6657 → 0,6679 | 0,8004 → 0,8012 | 61,0% → 85,0% | 100% → 26,8% |
| Смешанная | 0,6667 → 0,6662 | 0,8017 → 0,8005 | 58,0% → 83,0% | 100% → 25,2% |

К пятому шагу десятки рекомендаций по сгенерированной и реальной истории пересекаются лишь на 25–29%. Следующий реально прослушанный трек попадает в Top-10 базы в 4,5% случаев и на первом, и на пятом шаге; у RL-вариантов на пятом – в 3–4%. Повторные рекомендации встречаются всё чаще. Прогноз награды почти не падает, хотя истории разошлись. Поэтому пять прогнозов нельзя складывать и трактовать как пять измеренных откликов пользователя.

## Долгосрочная цель и ограничения

Использовал возвращение через 1–7 дней как доступный признак долгосрочного интереса. Этот признак неточен: пользователь мог вернуться по другой причине. Для реального сервиса в награду стоило бы включить качество прослушивания, возвращение после паузы, длительность следующих сессий и жалобы. Понадобились бы записи **всех показов**, включая треки, которые пользователь пропустил, их позиции и вероятности выбора старой системой. В Yambda `is_organic=0` отмечает неорганические *прослушивания*, а не все показанные треки. Поэтому модель отклика обучается на выбранных треках и может ошибаться именно там, где RL ищет высокий прогноз.

На исторических данных можно проверить прогноз на более позднем периоде, Recall/NDCG по фактическим прослушиваниям, повторы и концентрацию рекомендаций. При наличии логов показов можно было бы оценивать новую политику с поправкой на то, какие треки показывала старая система, если действия обеих политик достаточно пересекаются. В текущих данных для такой оценки нет информации. Проверить, повышает ли новая система возвращение и удовлетворённость людей, можно только в онлайн A/B-тесте.

Обучил модели с одним `seed` на одной фиксированной группе пользователей и ограничил каталог популярными на обучении треками. Доверительные интервалы показывают разброс между пользователями этой группы; они не учитывают, насколько изменился бы результат при другом обучении или другой группе. Следующий шаг – повторить опыт на нескольких выборках и `seed`, получить логи показов и проверить модель отклика на более широком наборе треков.

## Воспроизведение

Проверено на Python 3.10.5/macOS, PyTorch 2.14.1, NumPy 2.2.6, pandas 2.3.3, PyArrow 25.0.1, Apple MPS. Из этой папки:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python yambda_experiment.py --data-dir data --out-dir yambda_results
.venv/bin/python yambda_audit.py --data-dir data --results-dir yambda_results
```

Первый скрипт скачивает исходный Parquet (~352 MiB), проверяет SHA-256, обучает модели и записывает метрики и веса в `yambda_results`. Второй заново собирает примеры, проверяет разделение по времени и загружает веса для повторного расчёта тестовых метрик. Сырые данные из-за размера в репозиторий не включены. На CPU обучение займёт больше времени; веса могут немного различаться между устройствами, но разбиение и настройки фиксированы. Параметры основного скрипта перечислены в `--help`.

Дополнительный опыт на MovieLens можно запустить командами `.venv/bin/python experiment.py --data-dir data --out-dir results` и `.venv/bin/python audit.py --data-dir data --results-dir results`. Его результаты и ограничения описаны в [отдельном отчёте](MOVIELENS_REPORT.md).
