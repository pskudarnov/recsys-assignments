# Можно ли подбирать признаки для рекомендаций автоматически?

Эксперимент на данных онлайн-кинотеатра KION

## Что проверял

Представим, что нужно предложить пользователю фильмы на следующую неделю. Один способ – вручную посчитать признаки, которые описывают интересы пользователя и популярность фильмов, а затем обучить на них модель. Например, можно посчитать, сколько фильмов пользователь посмотрел за месяц и сколько просмотров получил каждый фильм за неделю.

Проверил, станет ли результат лучше, если поручить программе выбор периодов и связей, для которых считать признаки. Для сравнения обучил две модели CatBoost: одну на 23 признаках, выбранных вручную, другую – на признаках, которые программа сгенерировала и отобрала. Обе модели ранжировали одни и те же фильмы для одних и тех же пользователей.

**Короткий ответ:** на неделе, по которой выбирали число признаков, автоматический набор дал чуть лучший результат, но на итоговой тестовой неделе немного выиграли ручные. Так произошло на двух случайных выборках пользователей. Разница мала, и доверительные интервалы включают ноль. По этому эксперименту нельзя утверждать, что один способ устойчиво лучше другого.

## Данные и задача

Взял [открытый датасет KION](https://github.com/irsafilo/KION_DATASET). В полном архиве `data_en.zip` есть 5 476 251 строк взаимодействий за 13 марта – 22 августа 2021 года, а также сведения о пользователях и объектах каталога. Среди объектов есть фильмы и сериалы; ниже для краткости называю их фильмами. KION не публикует логи показов и кликов. Поэтому предсказываю, **появится ли в данных просмотр в следующие семь дней**. Вероятность клика после показа по этим данным оценить нельзя.

В README источника конечная дата указана как 22 августа 2022 года. Проверил закреплённый архив `data_en.zip`: минимальная дата в `interactions.csv` – 13 марта 2021 года, максимальная – 22 августа 2021 года. Даты в этом отчёте взяты из файла данных.

Для основного запуска случайно выбрал 3 000 пользователей, у которых была история до 5 июля 2021 года. Взял все 20 225 строк этих пользователей, не обрезая их истории. На каждом недельном срезе фильмы сортировались по числу просмотров до момента прогноза. Для каждого пользователя из этого списка брались первые 100 фильмов, которых ещё нет в его наблюдаемой истории. Эти 100 фильмов называются *кандидатами*: модель расставляет их в порядке рекомендации.

Метка для пары пользователь–фильм равна 1, если в следующие семь дней в данных появился просмотр этого фильма, и 0 в противном случае. Оба способа получают одинаковые пары и метки. Список кандидатов может различаться между пользователями, поскольку уже просмотренные фильмы исключаются отдельно для каждого.

У этих данных есть ограничение: для каждой пары пользователь–фильм KION хранит одну строку с **датой последнего просмотра**. Если фильм смотрели несколько раз, отдельных строк для каждого просмотра нет. Из-за этого нельзя точно восстановить всю историю просмотров. Ниже объясняю, как это влияет на выводы.

## Как устроено сравнение

### Ручные признаки

Собрал 23 признака в несколько групп:

- **Пользователь:** сколько просмотров было за 7, 30 и 180 дней; сколько дней прошло с последнего просмотра.
- **Фильм:** сколько просмотров он получил за 7, 30 и 180 дней; сколько дней прошло с последнего просмотра; насколько быстро растёт его популярность за последнюю неделю.
- **Интерес к жанру и фильму:** сколько фильмов того же основного жанра пользователь смотрел за 30 и 180 дней, какую долю они составляют в его истории и встречалась ли раньше конкретная пара пользователь–фильм. Основным считаю первый жанр из карточки фильма.
- **Сведения из справочников:** год выпуска, возрастной рейтинг, тип фильма, первый жанр, детский флаг, а также возрастная и доходная группы пользователя, пол и детский флаг.

Для связи с конкретным фильмом использован счётчик за 180 дней; для недельного тренда – `просмотры фильма за 7 дней / (просмотры за 30 дней + 1)`. Справочные категории передаются CatBoost как категориальные признаки. Один раз назначил категориям коды, прежде чем готовить данные для разных недель.

### Автоматический подбор

Программа строит счётчики для четырёх связей: фильм, пользователь, пользователь–фильм и пользователь–первый жанр фильма. Для каждой связи она пробует семь окон: **3, 7, 14, 30, 60, 120 и 180 дней**. Это 28 счётчиков. Вместе с теми же 5 производными и 9 справочными признаками получается 42 возможных признака.

Сначала CatBoost обучается на всех 42 признаках. Затем программа сортирует их по важности, рассчитанной **только на обучающих неделях**, и обучает модели на первых 8, 16 и всех 42. По качеству на валидационной неделе выбирается число признаков. В обоих запусках лучший результат на валидации дал вариант с 16 признаками. Программа выбирает только из тех вариантов подсчёта, которые я задал заранее. Новые SQL-запросы она не создаёт.

У ручной и автоматической моделей одинаковые настройки: 180 деревьев, глубина 6, темп обучения 0,06, коэффициент регуляризации 5, четыре вычислительных потока и seed 42. Не искал лучшие возможные настройки модели и способ отбора фильмов. Целью было сравнить признаки при одинаковых условиях.

## Как отделил прошлое от будущего

| Для чего нужны данные | Момент прогноза | Неделя, в которой ищем просмотр |
| --- | --- | --- |
| Обучение | 5, 12, 19 и 26 июля 2021 года | Семь дней после каждого прогноза |
| Выбор числа признаков | 2 августа 2021 года | 2–8 августа |
| Итоговая проверка | 9 августа 2021 года | 9–15 августа |

Для прогноза на дату `cutoff` используются только строки с `last_watch_dt < cutoff`. Неделя целевой метки начинается с `cutoff`, поэтому целевая строка не попадает в признаки. Когда делаю прогноз на 9 августа, просмотры за валидационную неделю уже относятся к прошлому и могут входить в историю. Метки тестовой недели не участвуют в выборе числа признаков.

В основном запуске четыре обучающих среза дали 1 200 000 пар, из них 1 100 положительных. Валидация и тест содержат по 300 000 пар: 203 и 183 положительные соответственно. Всего в тестовую неделю у выбранных пользователей есть 716 положительных пар, но лишь 183 из них попали в список кандидатов.

Главная метрика – **NDCG@10**. Она показывает, насколько удачно модель расположила фильмы в первой десятке: 1 означает идеальный порядок среди кандидатов, 0 – отсутствие полезного фильма в первой десятке. `Recall@10` показывает долю найденных просмотров **среди фильмов, попавших в кандидаты**. Обе метрики усредняются по всем 3 000 пользователям; если среди кандидатов пользователя нет будущего просмотра, его вклад равен нулю. ROC-AUC и LogLoss служат дополнительными метриками классификации. Эти числа отвечают на другие вопросы, поэтому сравнивать их с NDCG@10 напрямую нельзя.

## Что получилось

### Основной запуск: seed 2026

| Метод | Валидация NDCG@10 | Тест NDCG@10 | Тест Recall@10 | Тест ROC-AUC | Тест LogLoss |
| --- | ---: | ---: | ---: | ---: | ---: |
| Популярность фильма | – | 0,01181 | 0,01974 | 0,68530 | – |
| CatBoost, ручные признаки | 0,01453 | **0,01491** | **0,02247** | **0,88239** | **0,004411** |
| CatBoost, автоматический подбор | **0,01523** | 0,01467 | 0,02180 | 0,87500 | 0,004449 |

На валидации модель с 16 автоматически выбранными признаками обошла варианты с 8 признаками (NDCG@10 0,01509) и со всеми 42 (0,01475). Среди выбранных признаков оказались давность последнего просмотра пользователя, его активность за несколько периодов, популярность фильма, интерес к жанру и краткосрочный тренд. Некоторые из этих окон не входили в ручной список. Отдельно не проверял, помогло ли каждое из этих окон. На итоговой тестовой неделе автоматический набор преимуществ не дал.

Тестовая разница NDCG@10 «автоматический − ручной» составила **−0,00025**. 1 000 раз повторно выбирал из всех 3 000 тестовых пользователей и считал разницу; 95% интервал для разницы равен **[−0,00149; 0,00085]**. Интервал включает ноль. Поэтому нельзя уверенно сказать, что небольшая разница сохранится при другой выборке пользователей.

### Повторение: seed 2027

Повторил весь протокол на другом случайном наборе 3 000 пользователей. `Seed` в таблице – начальное число генератора случайной выборки. Настройки и правило выбора признаков остались теми же; валидация снова выбрала 16 признаков.

| Seed | Строк взаимодействий | Покрытие будущих просмотров кандидатами | Валидация: ручной / авто NDCG@10 | Тест: ручной / авто NDCG@10 |
| --- | ---: | ---: | ---: | ---: |
| 2026 | 20 225 | 25,6% | 0,01453 / 0,01523 | 0,01491 / 0,01467 |
| 2027 | 21 088 | 27,9% | 0,01763 / 0,01802 | 0,01709 / 0,01613 |

Во втором запуске тестовая разница равна **−0,00096**, а 95% интервал – **[−0,00255; 0,00068]**. Направление разницы повторилось, но и этот интервал включает ноль. Пока проверена только одна тестовая неделя. Чтобы проверить, сохранится ли результат со временем, нужны другие недели.

### Почему значения NDCG@10 невелики

В основном запуске список из 100 фильмов содержал лишь **25,6%** положительных пар тестовой недели. У 141 из 3 000 пользователей в кандидатах вообще был фильм, который они посмотрели. Если посмотреть только на этих пользователей, NDCG@10 равна 0,317 для ручной модели и 0,312 для автоматической. Так понятнее, почему общие значения низкие. Но главный результат по-прежнему нужно считать по всем пользователям.

Модель не может рекомендовать фильм, если его нет в списке кандидатов. Поэтому результаты описывают ранжирование выбранных 100 фильмов, а не готовую систему рекомендаций по всему каталогу. Возможно, модель хорошо распознаёт активных пользователей, но хуже выбирает фильмы внутри их списков. Это могло дать высокую ROC-AUC при низкой NDCG@10.

### Сколько это стоило

В основном запуске расчёт признаков занял около 0,35 секунды на недельный срез. Обучение ручной модели заняло 46,5 секунды, модели на всех 42 признаках – 52,0 секунды, модели с выбранными 16 признаками – 13,5 секунды. Весь запуск, включая чтение данных, поиск и оценку, занял 122,5 секунды при четырёх потоках.

Обучать уже найденную модель дешевле. Но поиск подходящих признаков занимает больше времени, чем обучение одной ручной модели: сначала приходится обучить модель со всеми признаками, а затем сравнить несколько наборов. Число оцениваемых пар растёт как `число пользователей × 100 кандидатов × число срезов`; переход от 100 фильмов ко всему каталогу резко увеличит затраты памяти и времени.

## Что ограничивает вывод

- **В данных видны не все прошлые просмотры.** `last_watch_dt` – дата последнего просмотра пары. Если пользователь смотрел фильм и до, и после среза, ранний просмотр не представлен отдельной строкой. Из этого датасета нельзя восстановить настоящий поток повторных просмотров.
- **Признаки для пары пользователь–фильм здесь не помогают.** У каждой пары пользователь–фильм в KION одна строка. После исключения уже наблюдавшихся фильмов из кандидатов все счётчики `user×item` равны нулю. Поэтому перебирать такие признаки в этом эксперименте нет смысла.
- **В список кандидатов попала лишь часть будущих просмотров.** При расчёте NDCG@10 и Recall@10 учитываю просмотренные фильмы только из этого списка. Если у пользователя таких фильмов нет, его вклад в метрики равен нулю. Это оценка второго этапа ранжирования, а не всего каталога.
- **Считаю, что сведения из справочников были известны на дату прогноза.** В KION нет дат их изменения, поэтому проверить это нельзя.
- **Пока проверил только два набора пользователей и одну неделю.** В каждом наборе по 3 000 пользователей. Для обучения несколько раз брал данные одних и тех же людей, поэтому часть пар без будущего просмотра повторяется. Для более уверенного вывода нужны новые периоды, больше пользователей и другие способы собирать кандидатов.
- **Это исследовательский эксперимент.** Во время работы уточнял правила проверки и перепроверял расчёты. Доверительные интервалы показывают, как меняется результат при повторном выборе пользователей из этой недели. Они не подтверждают гипотезу, заранее зафиксированную до начала эксперимента.

## Как повторить эксперимент

Нужны Python 3.12 и интернет для первой загрузки архива размером около 74 МиБ. Из каталога с этим README выполните:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python experiment.py --data data_en.zip --output results.json
```

Скрипт скачивает [архив KION, закреплённый за конкретным коммитом](https://github.com/irsafilo/KION_DATASET/blob/b242d2c781110902cbc8e5139f6fcefa64bbc845/data_en.zip) и проверяет SHA-256: `fddc5b2215bfff49bcfa21e464441f1fc6dc30f8f4afe41d3f23bf3fc45f3542`.

Для второго набора пользователей запустите:

```bash
.venv/bin/python experiment.py --data data_en.zip --output results_seed2027.json --seed 2027
```

Проверить границу временного окна и расчёт метрик можно командой:

```bash
.venv/bin/python -m unittest discover -s . -p 'test_*.py'
```

В моих запусках использовались NumPy 2.3.5, pandas 2.2.3, scikit-learn 1.9.1 и CatBoost 1.2.10. Время на другой машине может отличаться. Для быстрой проверки работы скрипта можно добавить `--users 300`; полученные метрики нельзя сравнивать с таблицами выше.

Код: [`experiment.py`](experiment.py). Проверки: [`test_experiment.py`](test_experiment.py). Полные результаты: [`results.json`](results.json) и [`results_seed2027.json`](results_seed2027.json).
